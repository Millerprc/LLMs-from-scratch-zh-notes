02文本数据：LLM 的"原料"是怎么被切碎的 产品相关性：高

为什么这章重要：LLM 的一切都是数字。它不会读"中文"或"英文"，只会读"一串整数"。这一章讲的就是人类语言怎么变成这串整数，以及为什么这个转换方式决定了 LLM 的所有边界。

2.1 Token：模型的"原子"

现代 LLM 不用"词"作单位、用"token"。Token 大概是这样的：

"Hello"
1 个 token
常见英文单词，常独享一个 token。
"你好"
2 个 token
中文字符密集，每个字常是独立 token。
"unhappiness"
3 个 token
"un" + "happiness"，拆成有意义的子词。
"2024-Q3"
5 个 token
数字不粘起来，按字符拆。

为什么这样设计？因为 LLM 的"词表"是固定的（GPT-2 是 50257 个 token）。如果按整词存词表，英语有上百万词，记不下；如果按字符存，每个 token 信息量太少。**BPE（字节对编码）**就是这个问题的折中：把高频子词合并成 token，低频的拆到字符。

2.2 实操：把一句话变成一串整数

1

读一行文本

import tiktoken

text = "Hello, do you like tea? Is this-- a test?"

tokenizer = tiktoken.get_encoding("gpt2")
ids = tokenizer.encode(text)
print("整数:", ids)
print("回原文:", tokenizer.decode(ids))

输出：[15496, 11, 466, 345, 588, 8887, 30, 220, 257, 287, 11, 220, 257, 6395, 5145, 30]

2

看 token 细节（最值钱的 debug 工具）

for tid in ids:
    print(f"{tid:>6}  →  ", repr(tokenizer.decode([tid])))

你会看到每个整数对应一截字符串。整数本身没有"意义"，只是词表里的索引。

PM 视角

当你看到"GPT-4 支持 128k token 上下文"，意思不是"它能读 12.8 万汉字"——是"它能读 12.8 万 token"。一个 token 大约 0.7 个英文单词 或 1-2 个汉字。所以 128k token ≈ 9 万汉字 ≈ 一本《老人与海》。

2.3 滑动窗口：怎么把一本书切成"训练样本"

LLM 不是"看完整本书再回答"，它是一个 token 一个 token 预测下一个。所以训练时要把文本切成固定长度的"窗口"，每个窗口里的 token 互相错一位——前 N 个是输入，第 N+1 个是目标：

同一本书被切成上千个 4-token 的窗口。每个窗口独立训练，没有跨窗口的"记忆"。

实操上 PyTorch 的 DataLoader 做这件事。代码不长，但概念重要：

from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
    def __init__(self, txt, tokenizer, max_length, stride):
        self.input_ids, self.target_ids = [], []
        token_ids = tokenizer.encode(txt)
        for i in range(0, len(token_ids) - max_length, stride):
            self.input_ids.append(torch.tensor(token_ids[i:i+max_length]))
            self.target_ids.append(torch.tensor(token_ids[i+1:i+max_length+1]))
    def __len__(self): return len(self.input_ids)
    def __getitem__(self, idx): return self.input_ids[idx], self.target_ids[idx]

def create_dataloader(txt, batch_size=4, max_length=256, stride=128):
    tokenizer = tiktoken.get_encoding("gpt2")
    dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)
    return DataLoader(dataset, batch_size=batch_size, shuffle=True, drop_last=True)

2.4 Token Embedding：把整数变成向量

整数喂不进神经网络，要先变向量。每个 token 对应一行向量，整本书籍的"含义"都藏在这张表里：

import torch

vocab_size = 50257      # GPT-2 的词表大小
output_dim = 256          # 向量维度（GPT-2 实际是 768 / 1024 / 1280）

token_embedding = torch.nn.Embedding(vocab_size, output_dim)
position_embedding = torch.nn.Embedding(1024, output_dim)  # 位置也得有向量

# 假设一个 batch：8 条样本、每条 4 个 token
input_ids = torch.randint(0, vocab_size, (8, 4))   # 8 × 4 整数

token_vecs = token_embedding(input_ids)              # → 8 × 4 × 256
pos_vecs   = position_embedding(torch.arange(4))  # → 4 × 256

input_vecs = token_vecs + pos_vecs    # 拼起来。000 越界时需要截断
print(input_vecs.shape)             # torch.Size([8, 4, 256])

▼ token + 位置叠加成"输入嵌入"。模型后续所有计算都从这堆向量开始。

PM 视角：为什么"上下文窗口"是个硬限制

位置 embedding 是按位置编号的（0 到 1024 / 4096 / 128000……）。模型只在训练过的位置上见过，超出训练过的位置它就懵了。这就是为什么"上下文 128k"不是你以为的"想读多长读多长"，是模型被造出来就只能处理 128k。

所以"长上下文"是各家模型实打实的技术壁垒，不是营销词。

✅ ch02 checkpoint

  • 能用 tiktoken 把任意文本编成整数 ID
  • 理解"token" ≠ "字" ≠ "词"，是一个被 BPE 算法决定的中间粒度
  • 能解释滑动窗口训练是怎么把一本书变成训练样本的
  • 能用一句话向同事解释"为什么长上下文是技术壁垒"

03注意力机制：模型怎么决定"看哪里" 产品相关性：高

为什么这章重要：注意力是 2017 年以来所有大模型的"心脏"。理解它，等于理解了 ChatGPT 怎么"听懂你说话"。不理解它，看任何 LLM 论文都只能看到表面。

3.1 直觉：上下文的相关性

假设模型在读 "The cat sat on the ____"，要预测下一个词。它需要回头看"cat"、"sat"、"on"——但"the"重要性低得多。

注意力机制干的事 = 给每个位置算一个"重要性分数"，然后用这个分数做加权平均。

一个形象的类比：你在会议室开会，每个人的发言对当下话题的"相关性"不一样。注意力机制就是让你自动把话筒递给相关性最高的人。

3.2 自注意力的三要素：Q、K、V

这是必须死记的三个字母：

Query (Q)
"我要找什么"
当前 token 提出的问题。比如"我现在是个名词，我后面应该跟什么动词？"
Key (K)
"我能被什么找到"
每个位置贴的"标签"。Query 跟谁的 Key 越像，谁就越被关注。
Value (V)
"我提供什么信息"
被选中之后，真正传递过去的内容。

类比：查字典。Q = 你要查的词；K = 字典里每个词条的索引；V = 词条的解释。你拿 Q 去和所有 K 比相似度，找最像的几个，然后用它们的 V 组成回答。

3.3 实操：从零搭一个自注意力

1

最简化版本（无权重）

先不看训练权重长什么样，写一个"纯注意力"：

import torch

inputs = torch.tensor([
    [0.43, 0.15, 0.89],  # Your
    [0.55, 0.87, 0.66],  # journey
    [0.57, 0.85, 0.64],  # starts
    [0.22, 0.58, 0.33],  # with
    [0.77, 0.25, 0.10],  # one
    [0.05, 0.80, 0.55],  # step
])

# 第 1 步：用第 2 个 token 当 query，算它跟所有 token 的相似度（点积）
query = inputs[1]
attn_scores = inputs @ query  # 每个 token 跟 query 的相似度

# 第 2 步：softmax 把分数变成权重（加起来等于 1）
attn_weights = torch.softmax(attn_scores, dim=0)

# 第 3 步：用权重对所有输入做加权平均，得到"语境向量"
context_vec = attn_weights @ inputs
print(context_vec)

三步走完，已经是一个完整的自注意力——只是没有"可学习权重"那一块。

2

加上可训练权重 Q/K/V

真实模型不是直接拿输入算点积，而是先把输入各自过一个线性层——这三层就是要训练的 Q/K/V 矩阵：

import torch.nn as nn

class SelfAttention(nn.Module):
    def __init__(self, d_in, d_out, qkv_bias=False):
        super().__init__()
        self.W_q = nn.Linear(d_in, d_out, bias=qkv_bias)
        self.W_k = nn.Linear(d_in, d_out, bias=qkv_bias)
        self.W_v = nn.Linear(d_in, d_out, bias=qkv_bias)

    def forward(self, x):
        Q = self.W_q(x)
        K = self.W_k(x)
        V = self.W_v(x)

        scores = Q @ K.transpose(-2, -1)          # 相似度矩阵
        weights = torch.softmax(scores / K.shape[-1]**0.5, dim=-1)  # 缩放 + 归一化
        return weights @ V                        # 加权求和

torch.manual_seed(123)
sa = SelfAttention(d_in=3, d_out=2)
out = sa(inputs)
print(out.shape)  # torch.Size([6, 2])

缩放因子 √d_k 是为了防止 d_k 太大时 softmax 饱和（所有权重挤到一个 token 上）。

3

因果掩码：让模型看不到未来

GPT 是"从左往右"生成，所以训练时当前位置不能偷看后面。用一个上三角矩阵盖住：

mask = torch.triu(torch.ones(6, 6), diagonal=1)  # 上三角为 1
scores = scores.masked_fill(mask.bool(), -torch.inf)  # 未来位置 = -∞
weights = torch.softmax(scores / K.shape[-1]**0.5, dim=-1)
# 未来位置 softmax 后 = 0，不参与加权

这就是为什么 GPT 能"自回归生成"——它的训练规则就是"只能看左边"。

3.4 多头注意力：拆成 N 份，各看各的

一个注意力只能学一种"看问题的方式"。多头注意力 = 把 Q/K/V 拆成 N 份，每份独立做注意力，再拼起来。

实际实现（这就是 ch03 末尾最终版的多头注意力）：

class MultiHeadAttention(nn.Module):
    def __init__(self, d_in, d_out, n_heads, context_len, dropout, qkv_bias=False):
        super().__init__()
        assert d_out % n_heads == 0
        self.n_heads, self.head_dim = n_heads, d_out // n_heads

        self.W_q = nn.Linear(d_in, d_out, bias=qkv_bias)
        self.W_k = nn.Linear(d_in, d_out, bias=qkv_bias)
        self.W_v = nn.Linear(d_in, d_out, bias=qkv_bias)
        self.out_proj = nn.Linear(d_out, d_out)
        self.dropout = nn.Dropout(dropout)
        self.register_buffer('mask', torch.triu(torch.ones(context_len, context_len), diagonal=1))

    def forward(self, x):
        b, n_tokens, _ = x.shape
        Q = self.W_q(x).view(b, n_tokens, self.n_heads, self.head_dim).transpose(1, 2)
        K = self.W_k(x).view(b, n_tokens, self.n_heads, self.head_dim).transpose(1, 2)
        V = self.W_v(x).view(b, n_tokens, self.n_heads, self.head_dim).transpose(1, 2)

        scores = Q @ K.transpose(-2, -1)
        scores.masked_fill_(self.mask.bool()[:n_tokens, :n_tokens], -torch.inf)
        weights = torch.softmax(scores / self.head_dim**0.5, dim=-1)
        weights = self.dropout(weights)

        ctx = (weights @ V).transpose(1, 2).contiguous().view(b, n_tokens, -1)
        return self.out_proj(ctx)
PM 视角：为什么 attention 是"卡脖子"

注意力的计算复杂度是 O(n²)——上下文长度翻倍，计算量翻 4 倍。所以"上下文 128k"不是"免费升级"，是每 token 算得更多。

这也是为什么业内出现一堆"省钱变种"：Sliding Window Attention（只看邻近）、GQA（多 query 共享 key）、MLA（压缩 KV）。ch04 后面那些 bonus 子目录都是这些变种。

产品含义：你的产品要给模型"塞多长 prompt"，决定了你买哪家 API 更合适。

  • 能解释"为什么 GPT 不能看到未来 token"
  • 知道"多头注意力"是为了让模型同时关注多种关系

04GPT 模型：把所有零件拼起来 产品相关性：极高

为什么这章是核心：前面三章（ch01-03）都在做"原料"——数据、token、注意力。这一章把它们组装成一个真正能"生成 token"的模型。

4.1 一个 GPT block 是什么样的

GPT 不是只有一个大块头，而是把同一个 block 重复 N 次堆起来。每次 block 干两件事：

通信层
Multi-Head Attention
"让当前位置看看整个上下文，决定权重"
思考层
Feed-Forward Network
"基于已经加权过的信息，做一次非线性变换"

中间还有 LayerNorm（标准化）和残差连接（避免深层梯度消失）：

GPT-2 124M 用了 12 个这样的 block 堆叠。每个 block 内部张量维度是 768。光是这些 block 的参数就占了一亿出头。

4.2 实操：一个最小可跑的 GPT-2 124M

完整代码很长，下面是简化骨架，跑通就能理解结构。完整版在 ch04/01_main-chapter-code/ch04.ipynb：

import torch
import torch.nn as nn

GPT_CONFIG_124M = {
    "vocab_size":   50257,
    "context_len":  1024,
    "emb_dim":      768,
    "n_heads":      12,
    "n_layers":     12,
    "drop_rate":    0.1,
    "qkv_bias":     False,
}

class LayerNorm(nn.Module):
    def __init__(self, emb_dim):
        super().__init__()
        self.eps = 1e-5
        self.scale = nn.Parameter(torch.ones(emb_dim))
        self.shift = nn.Parameter(torch.zeros(emb_dim))
    def forward(self, x):
        mean = x.mean(dim=-1, keepdim=True)
        var  = x.var (dim=-1, keepdim=True)
        return self.scale * (x - mean) / torch.sqrt(var + self.eps) + self.shift

class FeedForward(nn.Module):
    def __init__(self, emb_dim):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(emb_dim, 4 * emb_dim),
            nn.GELU(),
            nn.Linear(4 * emb_dim, emb_dim),
        )
    def forward(self, x):
        return self.net(x)

class TransformerBlock(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.att = MultiHeadAttention(
            d_in=cfg["emb_dim"], d_out=cfg["emb_dim"],
            n_heads=cfg["n_heads"],
            context_len=cfg["context_len"],
            dropout=cfg["drop_rate"], qkv_bias=cfg["qkv_bias"],
        )
        self.ff   = FeedForward(cfg["emb_dim"])
        self.norm1 = LayerNorm(cfg["emb_dim"])
        self.norm2 = LayerNorm(cfg["emb_dim"])
        self.drop = nn.Dropout(cfg["drop_rate"])

    def forward(self, x):
        x = x + self.drop(self.att(self.norm1(x)))   # 残差 + 通信
        x = x + self.drop(self.ff (self.norm2(x)))   # 残差 + 思考
        return x

class GPTModel(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.tok_emb = nn.Embedding(cfg["vocab_size"], cfg["emb_dim"])
        self.pos_emb = nn.Embedding(cfg["context_len"], cfg["emb_dim"])
        self.drop_emb = nn.Dropout(cfg["drop_rate"])
        self.trf_blocks = nn.Sequential(
            *[TransformerBlock(cfg) for _ in range(cfg["n_layers"])]
        )
        self.final_norm = LayerNorm(cfg["emb_dim"])
        self.out_head = nn.Linear(cfg["emb_dim"], cfg["vocab_size"], bias=False)

    def forward(self, in_idx):
        batch_size, seq_len = in_idx.shape
        tok = self.tok_emb(in_idx)
        pos = self.pos_emb(torch.arange(seq_len, device=in_idx.device))
        x = self.drop_emb(tok + pos)
        x = self.trf_blocks(x)
        x = self.final_norm(x)
        logits = self.out_head(x)               # 每个位置预测 vocab_size 个词的概率
        return logits

# 跑一下
torch.manual_seed(123)
model = GPTModel(GPT_CONFIG_124M)
print(f"参数总数: {sum(p.numel() for p in model.parameters()):,}")
# 输出: 参数总数: 163,063,616 — 接近 1.24 亿（带 embedding 共享会正好 124M）

4.3 三个必须记住的"模型尺码"

PM 视角：为什么"参数量"不是越大越好

直觉上，参数多 = 容量大 = 效果好。但工程上要付出三个代价：

  • 推理延迟：单次生成要算 N×d² 次乘加。GPT-2 XL 比 124M 慢 12 倍。
  • 显存：fp16 也要 3 GB 显存，int4 量化后 ~1 GB。
  • 训练成本：1.56B 完整训练要 ~$400 GPU 时。

所以"开源 7B 模型"是 2023 年后的 sweet spot——再大个人跑不起，再小能力不够。

5.1 训练循环的核心结构

LLM 的训练不是"魔法"——就是一个常规的 PyTorch 训练循环，加几个 LLM 特化的细节：

def train(model, train_loader, val_loader, cfg, device):
    optimizer = torch.optim.AdamW(
        model.parameters(),
        lr=cfg["learning_rate"], weight_decay=cfg["weight_decay"]
    )

    for epoch in range(cfg["num_epochs"]):
        model.train()
        for input_batch, target_batch in train_loader:
            input_batch  = input_batch.to(device)
            target_batch = target_batch.to(device)

            logits = model(input_batch)              # 前向
            loss = calc_loss(logits, target_batch, cfg)  # 算 cross-entropy
            loss.backward()                          # 反向
            optimizer.step()                         # 改参数
            optimizer.zero_grad()

        # 评估
        model.eval()
        with torch.no_grad():
            val_loss = evaluate(model, val_loader, device, cfg)
        print(f"epoch {epoch}: train_loss={loss.item():.4f}  val_loss={val_loss:.4f}")

def calc_loss(logits, targets, cfg):
    # logits 形状: (batch, seq_len, vocab_size)
    # 拉平成 (batch*seq_len, vocab_size) 和 (batch*seq_len,)
    loss = torch.nn.functional.cross_entropy(
        logits.flatten(0, 1), targets.flatten()
    )
    return loss

5.2 Loss 是什么——一句话版本

Cross-entropy 衡量"模型给的概率分布有多接近 one-hot"。

  • 模型说"下一个 token 是 X 的概率 = 80%"，实际 X → loss 小
  • 模型说"X 概率 = 5%"，实际是 X → loss 大

LLM 训练里，loss 从 ~10 一路降到 ~2-3 表示模型基本"学会"了语言模式。

5.4 生成文本：贪心 vs sampling

def generate(model, idx, max_new_tokens, context_size, temperature=0.0, top_k=None):
    for _ in range(max_new_tokens):
        idx_cond = idx[:, -context_size:]                 # 截到上下文长度
        with torch.no_grad():
            logits = model(idx_cond)                      # (batch, seq, vocab)

        logits = logits[:, -1, :]                      # 只看最后一个位置
        if top_k is not None:
            v, _ = torch.topk(logits, top_k)
            logits[logits < v[:, [-1]]] = -torch.inf
        if temperature > 0.0:
            logits = logits / temperature
            idx_next = torch.multinomial(torch.softmax(logits, dim=-1), num_samples=1)
        else:
            idx_next = torch.argmax(logits, dim=-1, keepdim=True)  # 贪心
        idx = torch.cat((idx, idx_next), dim=1)
    return idx

PM 视角：temperature 和 top-k 怎么影响产品体验
  • temperature = 0（贪心）：每次选概率最高的。确定性强，但容易循环重复、话术化。
  • temperature = 1：按概率采样。生成多样，但有时会跑偏。
  • top-k = 40：只在概率最高的 40 个 token 里采样。砍掉"长尾胡言乱语"。

经验值：

  • 代码生成 / 工具调用 → temperature 低（0.0 - 0.3）
  • 创意写作 / 头脑风暴 → temperature 高（0.7 - 1.2）
  • 客服 / FAQ → temperature 接近 0 + top-k 小（10-20）

PM 视角：为什么微调小模型有时比改 prompt 更划算

送 GPT-4 API 处理一次请求 = ~$0.01-0.05。送自训 7B 模型（开源）推理一次 = ~$0.0001（自托管）。

算账：

  • 100 万次/月 × GPT-4 = $10,000 - 50,000
  • 100 万次/月 × 自托管 7B = $200 - 500（GPU 摊销 + 电）

当你的需求稳定、需要量大时，微调 + 自托管是几十倍的成本下降。但需要：

  • 领域数据（通常 1-10 万条指令）
  • 技术团队做数据 + 训练 + 部署
  • 对模型能力上限有合理预期（7B 模型 ≠ GPT-4）

7.5 DPO：从"会答"到"答得对齐人类偏好"

ch07 后半部还有一节 DPO（Direct Preference Optimization）。它解决的是"模型答对了指令，但答得不够好"——典型场景是"礼貌度不够"、"带偏见"、"胡编程度太高"。

DPO 的核心数据：同一个指令的多个回答 + 人类评分：

{
  "prompt":   "解释什么是通胀",
  "chosen":   "通胀是货币购买力下降……（温和、详尽、不偏激）",
  "rejected": "通胀就是钱不值钱了，这都懂？（粗暴、简略）"
}

训练目标：模型给 chosen 的概率要显著高于 rejected。

PM 视角：RLHF / DPO 的产品含义

DPO 是 ChatGPT 之后所有"对齐"工作的核心。技术上只是一行 loss 公式的修改，业务上却是"产品调性"的承载：

  • 客服模型用客服语料 DPO → 答得"像客服"
  • 儿童教育模型用儿童语料 DPO → 答得"适合小朋友"
  • 法务模型用合规语料 DPO → 不给"危险建议"

所以"调 prompt"和"做 DPO"的边界是：prompt 改的是"问什么"，DPO 改的是"答什么风格"。
